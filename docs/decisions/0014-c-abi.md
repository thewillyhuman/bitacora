# 0014. The C interface of the client

Status: accepted · 2026-11-26

## Context

The design asks for "a C ABI over the Rust client, with a generated header",
because PostgreSQL integration needs it (section 13, "Other languages"). It
says nothing about what that interface looks like. The Rust client is
asynchronous, reports errors as enums with data, and is configured through
Rust structures. None of that crosses into C as it is. A PostgreSQL backend
adds its own constraints: it is one thread, it is created by `fork`, it is
driven by signals, and it leaves a function with `longjmp` when something
fails.

## Decision

**Calls block, on a runtime the client owns.** Each client starts a Tokio
runtime with a few threads. A call spawns its work on that runtime and
blocks the calling thread until the work has an answer; calls that wait for
the cluster take a timeout. An asynchronous interface was considered and
left out: it needs callbacks, and a callback that runs on a library thread
inside a PostgreSQL backend can do almost nothing safely. A blocking call
with a timeout is something every C program can use, and an event loop can
be built on top of it with a thread.

**The calling thread never runs the client's code.** It checks arguments,
waits and copies results. This is more than tidiness: threads that are
started later, for work that blocks, are then always started by a library
thread and never by whichever application thread happens to make a call. So
every library thread descends from the thread that connected and has the
signal mask that thread had while it connected. A host whose signal handlers
must run on its own thread blocks its signals around the connect and is
done. The price is that the work of a call must own what it uses, which
costs a few reference counts and a copy of the stream's name.

**A status code and a message per thread.** Every function that can fail
returns a `bitacora_status`. The codes separate what a caller handles
differently, not what the Rust client happens to name: fenced, indeterminate
and truncated each have their own, because they are the promises of the
design and each asks for a different reaction; "not found", "already
exists", "invalid argument" and "unavailable" are the usual ones; "nothing
new" is separate from "timed out", because a follower that hears nothing is
healthy and an append that hears nothing is in doubt. An append never
returns "unavailable": what the library does not know, it reports as
indeterminate. Every case of the client's error enums is mapped in one file,
`status.rs`, with wildcard arms denied by lint there, so a new case fails
the build until someone decides what C sees. The text of the error is kept
per thread and read with `bitacora_last_error_message`; it is for logs.
Truncation reports the low-water mark through an output argument, because a
program must not parse a message to learn where it can resume.

**The cluster configuration stays TOML.** C passes the path or the text of
the file every bitacora program reads. Mirroring the configuration as C
structures would freeze its shape into the ABI and need a change here for
every new kind of object store. The few things C does set are in structures
that begin with their own size, so that fields can be added at the end
without breaking programs compiled against an older header.

**The header is generated and checked in.** cbindgen generates
`src/c/include/bitacora.h` from the Rust source, as a library called from a
test, without running Cargo, so it works inside the Bazel sandbox. The
header is committed so that a C user reads it without Rust tooling. The test
generates it again and fails when the committed copy differs by a byte;
`hack/update_c_header.sh` runs the same test in a mode that writes the file.
The doc comments of the exported items are therefore written for a C reader:
they are the header's documentation.

**A second proof, by a C compiler.** A generated header agrees with the Rust
source by construction, but nothing in Rust checks that the library exports
the symbols, that the archive links, or that the statuses come out of a real
cluster. C programs do: one covers every argument error and runs against
both the static and the shared library; one goes through the life of a
stream against etcd, replicas and a controller. They are compiled as C11
with warnings as errors.

**`unsafe` in this crate only, and little of it.** The workspace denies
`unsafe`; this crate allows it, because a pointer from C cannot be used
without it. The ways a pointer becomes something safe live in one file,
`arguments.rs`: a null pointer where one is required and text that is not
UTF-8 are reported as invalid arguments and nothing is dereferenced. Each
entry point has one `unsafe` call per argument, with the caller's guarantee
stated next to it and repeated in the header. Every entry point runs inside
`catch_unwind`: a panic becomes `BITACORA_STATUS_INTERNAL`, since unwinding
into C is undefined behaviour.

## Consequences

- A client is not usable across `fork`. The child has the handles and none
  of the threads. PostgreSQL has to connect in the process that uses the
  client; the documentation says so first.
- A signal does not interrupt a call. Programs that must react to signals
  give their calls a timeout.
- An append copies its payload once. Passing the caller's buffer through
  would tie its lifetime to work that continues after a timed-out call
  returns.
- The C tests need a C compiler on the machine that runs the check. Bazel
  uses the one it finds; the Rust side stays hermetic.
- cbindgen and its dependencies are in `Cargo.lock`, for tests only.
- On macOS the static library has to be linked together with the Security
  and CoreFoundation frameworks, which an archive cannot say itself; the
  Bazel target and the documentation do.
- The interface version, `BITACORA_ABI_VERSION`, is kept by hand. It changes
  only when a program compiled against the old header could misbehave with
  the new library.
